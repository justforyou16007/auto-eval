# Acceptance Gate: DRIVE vs ACQUIT

Adapted from ARIS `acceptance-gate.md`.

## Principle

The DRIVE vs ACQUIT principle separates tasks that can be judged by the
same model (DRIVE) from tasks that MUST be cross-model (ACQUIT).

## Per-Stage ACQUIT Audit (issue #5 redesign)

**All 5 pipeline stages are DRIVE workers.** Each stage has a companion
**ACQUIT audit skill** that audits whether the worker honestly completed its
task. The audit flow for every stage is:

1. **Read the worker's output** (the artifact the worker claims to produce).
2. **Check three things**:
   - a. **Completeness** — did the worker truthfully do the work (no stubs,
     placeholders, or falsely-claimed artifacts)?
   - b. **Usability** — is the output real and usable (actually run & verify
     the result — e.g. run `docker compose`, run evaluator `--help`, parse
     the report HTML, re-run the affected task)?
   - c. **Stage-specific check** — for task-generation, verify tasks align
     with real-world scenarios; for env, verify constraint match; etc.

| Stage | DRIVE worker | ACQUIT audit | Audit checks |
|-------|--------------|--------------|--------------|
| 1 | `task-gen` | `task-audit` | completeness, usability, **alignment** |
| 2 | `env-gen` | `env-audit` | completeness, usability (run compose), constraint match |
| 3 | `rubric-gen` | `rubric-audit` | completeness, usability (run evaluators), coverage |
| 4 | `report-gen` | `report-audit` | completeness, usability (parse + cross-check), provenance |
| 5 | `feedback-align` | `feedback-audit` | completeness, usability (re-run task), status accuracy |

> **Key change.** Previously `rubric-gen` was itself the ACQUIT role and
> `feedback-align` was `DRIVE_ACQUIT` (verifying its own changes). Both
> conflated the worker with its auditor. After the redesign, both are pure
> DRIVE workers and their ACQUIT responsibilities moved to the dedicated
> `*-audit` skills above.

## DRIVE Roles

DRIVE skills generate artifacts. They can be performed by the same model
because they are creative/constructive, not evaluative.

| Skill | DRIVE Aspect |
|-------|-------------|
| `task-gen` | Generate task specifications |
| `env-gen` | Generate Docker environment configurations |
| `rubric-gen` | Generate rubric criteria + evaluator scripts |
| `report-gen` | Generate HTML verification reports |
| `feedback-align` | Record + analyze + apply feedback changes |

**Script evaluators** generated by `rubric-gen` are also DRIVE — the
mechanical checks themselves are deterministic; verifying that they are
*correct and complete* is the `rubric-audit` skill's ACQUIT job.

## ACQUIT Roles

ACQUIT skills define quality or correctness. They MUST use a different
model family than the one that generated the artifact.

| Skill | ACQUIT Aspect |
|-------|--------------|
| `task-audit` | Task completeness, usability, real-world alignment |
| `env-audit` | Environment completeness, usability (runs compose), constraint match |
| `rubric-audit` | Rubric completeness, usability (runs evaluators), coverage |
| `report-audit` | Report completeness, usability (parses + cross-checks), provenance |
| `feedback-audit` | Change completeness, usability (re-runs task), status accuracy |

No DRIVE worker audits its own output. Each worker's `audited-by`
frontmatter field names the ACQUIT skill that audits it.

## Hard Invariants

1. **Cross-model review always on**: Any ACQUIT evaluation must use a
   different model family than the DRIVE generation.
2. **Reviewer independence always on**: The evaluating model must not have
   been involved in the original generation.
3. **Script evaluators can self-judge**: Mechanical checks (exit code,
   format validation) are deterministic and do not require a different model.
4. **LLM judge evaluators cannot self-judge**: Any evaluation involving
   semantic judgment must be cross-model.
5. **Workers never ACQUIT themselves**: No DRIVE worker verifies its own
   output; every stage delegates verification to its `*-audit` ACQUIT skill.

## Verification

For ACQUIT operations, the verifying agent must:
- Be from a different model family (e.g., if task-gen used Claude,
  task-audit must use GPT or another model)
- Report which model family performed the verification
- Record the verification result in the artifact metadata
